一次改造的解剖

iirose 点歌插件新增 QQ 音乐源 · 从可行性验证到上线 · 2026-09-24
插件原本只会点网易云的歌。这次让它也能点 QQ 音乐 —— 但 QQ 的会员歌只给 60 秒试听， 完整版纯前端拿不到。所以最后做成：能完整播的就用 QQ，拿不到就自动改点网易云同名单曲， 并且把"为什么换了"明说给你。
往下每节都能点、能拖。全程约 8 分钟。

一、骨架：一次点播要穿过五层

点开每一层，看它负责什么、这次改了什么。这段就是整个插件的结构。

协议层把"要放什么歌"拼成 iirose 认得的两条消息

一条是聊天框里的媒体卡片，一条是触发播放的事件。平台用类型码区分音源：网易云是 @0，QQ 音乐是 @2。

<卡片>  m__4@2>歌名>歌手>封面>颜色>码率
<事件>  &1{"s":"播放地址","d":时长,"c":"封面","n":"歌名",
              "r":"歌手","b":"@2","o":"原站链接","l":"歌词"}

这次改动：类型码从写死改成参数，网易云那条路保持传 @0，一行代码没动它的行为。

▼
数据层去两个平台把歌搜出来、把播放地址要来

网易云走 GD-Studio，QQ 走 api.vkeys.cn。两边的返回字段完全不同，所以中间有一层"翻译"，把它们统一成同一个形状，并给每首歌打上 source 标记。

{ source:'qq', mid:'004dPfPq4VgCmz', name:'莫扎特钢琴曲k448',
  singer:'jaycd', duration:264, kbps:319, cover:'…' }

那个 source 是后面所有分岔路口的依据 —— 没有它，整个改造会以最隐蔽的方式出错（见第四节）。

▼
判定层这首 QQ 歌到底是完整版，还是 60 秒试听

接口不会老实告诉你答案，只能靠间接信号推断（第三节有可拖动的实验台）。判完给一个 complete: true/false。

▼
决策层按 source 走哪条路、判不完整时怎么办

全部逻辑只有一句分岔，然后各自走到底：

if ((song.source || 'netease') !== 'qq') return sendNetease(song);
// 剩下的都是 QQ 的路：判完整 → 发 @2；不完整 → 回退网易云同名 → 发 @0；都失败 → 明确报错

第二节有个模拟器，可以点着看三种歌分别走哪条路、发出什么消息。

▼
界面层让你看得见发生了什么

搜索结果带来源徽标（红=网易云 / 绿=QQ）与时长；状态栏在回退过程中持续说话： QQ 只给 60 秒试听片段（会员曲目），正在回退网易云… —— 因为整条回退链最坏要 70 秒， 全程沉默就等于"点了没反应"。

三、实验台：判据在哪一秒会翻车

判定"是不是试听"，第一版用的办法是拿文件大小 ÷ 歌曲时长反推码率： 完整歌最少也有 128kbps，试听只有 60 秒的内容却配了整首歌的时长，比例会崩，所以低于 64kbps 就判试听。 听起来很聪明 —— 拖动下面的滑块，看看它在什么情况下失效。

结论：当歌短到 120 秒左右时，0.92MB ÷ 120s ≈ 64kbps —— 正好压在阈值上， 比值法会把 60 秒试听判成完整版，于是用户听到一段 60 秒就没了，还以为自己点成功了。 而它错得毫无征兆：不做实验，你根本不会想到去试"短歌"这个角落。

后来发现接口其实返回了实际文件码率：试听恒 28kbps、完整 319kbps。 这个信号和歌多长无关，短歌也不会漏判 —— 换判据之后，这个角落自动消失了。 判据要选"不会因为边界情况而失效"的那一个。

四、最危险的不是报错，是"悄悄做对了一件错事"

QQ 音乐的歌曲 id 和网易云的 id 都是数字，值域重叠。如果代码不看 source、 直接拿 QQ 的 id 去调网易云接口 —— 网易云不会报错，它会返回另一首歌。 于是你点了 A，房间播放的是 B，全程没有任何异常提示。

检查项为什么必须做
入口带 source两个平台的数据长得一样，只能靠标记区分
出口传对应类型码卡片与事件的类型码都要对，否则平台会按错误音源解释
降级路径也走同一套分流回退到网易云时，消息要重新按网易云拼（@0）

这条是独立审查（子 agent）标出的最高危项。它的原话：会"静默播成另一首歌，并被标成网易云源"。

五、"我改完了，为什么还是旧版？"

点开下面这道题，跟着排查一遍 —— 这是这次真实卡住的地方，而且卡了三层。

1
CDN 缓存（我这边负责）
jsdelivr 对"分支地址"有小时级缓存。我推完代码立刻去拉线上文件，拿到的还是上一版。
排查：用 commit 地址拉一次（这类地址永不缓存）—— 内容对得上就说明仓库没问题，剩下全是缓存。
处理：调 jsdelivr 的 purge 接口刷掉，而且验证哪个地址就 purge 哪个地址（带 @main 和不带是两个独立条目）。
2
浏览器缓存（你这边）
哪怕 CDN 已经更新，你机器上的浏览器可能还留着旧的 JS。实测响应头：默认地址 max-age=604800（7 天）。
处理：Ctrl+F5 强刷（普通 F5 会复用缓存），或在地址后面加 ?v=数字 骗它当成新文件。
3
注入地址存在浏览器里（最容易忽略）
iirose 把脚本地址存在 localStorage 的 extJs 里。 光改桌面上的记录文件没用 —— 必须回到 iirose 页面里重新 js 粘贴一次地址， 否则浏览器压根不会去请求新文件。

三道门都过了还没新版，就把控制台切到 mainFrame 上下文，执行 window.__IIROSE_DIANBO_VERSION__：返回版本号说明新版已加载，返回 undefined 说明脚本还是旧的。

六、这次踩的六个坑

点开看现象、根因和能带走的教训。

1拿到了直链，却不出声
第三方给的播放地址是 http://，而 iirose 是 https 页面，被浏览器当"混合内容"拦掉 —— 而且不报错。
教训：外部资源进页面前先检查协议；"拿到了但没反应"优先怀疑这一层。
2点周杰伦《晴天》，回退成了翻唱版
回退只按歌名找同名单曲，没管歌手。网易云没有周杰伦版权，于是匹配到了《晴天(深情版)》。
教训：匹配条件要带上"人物"维度；而且换了谁必须写进提示，不能让你以为放的是原唱。
3提示写着"只给 269 秒试听片段"
同一个 duration 字段，一处含义是"整首歌多长"，另一处被当成"试听多长"。试听其实恒为 60 秒。
教训：字段语义要写在代码里；一个数字两种含义是 bug 温床。错误的事实比没有提示更糟。
4本地自测时"QQ 音乐凭空消失"
本地启动脚本指向的是另一份老副本，那里没有 QQ 代码。
教训：一个项目只留一个源，副本迟早背叛你。
5用户输入一串 14 位数字，被当成歌曲 id
链接识别的"兜底规则"太宽：凡 14 位字母数字都认。
教训：兜底要带防误判条件（要求字母+数字混合），宁可漏判也别错判。
6回退过程 70 秒里，界面一声不吭
取直链 + 搜同名 + 再取一次直链，每层都有超时，最长叠到 70 秒。状态栏却还停在"找到 3 首"。
教训：凡是超过两三秒的操作，都要让用户看见进度；沉默等于"坏了"。
